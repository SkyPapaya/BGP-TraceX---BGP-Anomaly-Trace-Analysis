## 1. 系统概述

### 1.1 项目背景

BGP（Border Gateway Protocol，边界网关协议）是互联网的核心路由协议，但其设计之初缺乏充分的安全机制，导致前缀劫持、路由泄露、路径伪造等安全事件频发。传统检测方法仅能判断"是否存在异常"，但对于异常的具体类型、攻击者身份、攻击手段等关键信息无法给出明确结论。

BGP-TraceX 3.0 是一个面向 BGP 异常归因的研究型系统，核心目标不仅是检测异常，更重要的是输出完整的溯源结论。

### 1.2 系统能力

系统接收 BGP 告警（单条或批量），经过多轮推理和工具调用，输出以下结构化结论：

| 输出项 | 说明 | 可选值 |
|--------|------|--------|
| 异常类型 | 判定告警对应的攻击类别 | `HIJACK` / `LEAK` / `FORGERY` / `BENIGN` |
| 最可能攻击者 | 归因到具体 AS 号 | AS 号或 `UNKNOWN` |
| 置信度 | 结论的可信程度 | `High` / `Medium` / `Low` / `Uncertain` |
| 推理链 | 每轮思考过程与工具调用记录 | 结构化 JSON |
| 批量一致性 | 多条告警间的统计一致性信息 | 共识率、主导类型等 |

### 1.3 适用场景

- BGP 安全研究中的异常归因实验
- 多方法（LLM/规则/RAG）对比评估
- 合成基准与真实事件的溯源准确性验证
- BGP 异常检测学术论文的实验支撑
- 网络安全课程中 BGP 安全教学的辅助工具
- 网络运营商的路由异常事件事后分析

### 1.4 技术路线

系统采用"RAG 检索增强 + LLM 推理 + 工具调用"的混合架构。LLM 作为推理核心，通过调用专业取证工具获取证据，并结合历史案例库（RAG）的相似案例参考，最终通过批量纠偏机制输出一致、可解释的溯源结论。

### 1.5 与传统检测方法的区别

传统 BGP 异常检测系统（如 BGPmon、ARTEMIS）主要依赖固定规则或统计阈值来判断"是否存在异常"，其局限性体现在三个方面：第一，无法区分异常的具体类型，将劫持、泄露、伪造混为一谈；第二，无法定位攻击者 AS，只能报告受影响的 prefix；第三，缺乏可解释性，输出结果没有推理过程支撑。BGP-TraceX 3.0 针对这三个痛点，引入了 LLM 驱动的多轮推理机制，每一步推理都调用专业取证工具获取证据，同时参考历史案例的相似模式，最终输出包含类型判定、攻击者归因、置信度评估和完整推理链的结构化结果。此外，批量溯源模式能够利用多条告警之间的关联信息进行交叉验证，这是传统单条告警检测方法无法做到的。

### 1.6 系统局限性

作为研究原型系统，BGP-TraceX 3.0 存在以下已知局限，使用者应在实验设计中予以考虑：

- **LLM 依赖性**：系统的核心推理能力依赖 DeepSeek 大语言模型，模型的服务可用性、API 响应延迟和版本变更可能影响实验的稳定性和可复现性。
- **工具数据质量**：RPKI、地理位置、拓扑等工具依赖外部数据源（RIPEstat API 等），数据源的覆盖率和时效性直接影响取证结果的完整度。
- **Neo4j 可选性**：图拓扑分析功能需要 Neo4j 数据库支持，未启动时自动退化，此时图分析工具不参与推理。
- **类别歧义**：短路径场景下 FORGERY 和 LEAK 仍存在分类歧义，这是 BGP 安全领域的固有难点，系统通过置信度标记来反映不确定性。
- **规模限制**：系统针对实验评估场景优化，未针对大规模实时告警流进行工程化改造，不适合直接部署为生产级监控系统。

### 4.2 快速判定机制

系统在进入完整推理流程之前，会先执行快速预检，对明显案例提前判定，节省计算资源。

**BENIGN 快速判定**：当所有告警同时满足以下条件时，系统直接判定为 `BENIGN`：
- Origin AS 与预期合法持有者完全匹配
- AS_PATH 长度不超过两跳
- 无其他异常信号

**FORGERY 快速标记**：当告警满足以下条件时，系统标记为疑似 `FORGERY` 并优先处理：
- Origin AS 与预期合法持有者匹配（看似合法）
- 但 AS_PATH 长度达到四跳或以上（长路径暗示可能伪造）
- 该标记引导后续的 `forgery_check` 工具进行深入验证

快速判定机制在实际实验中能过滤掉约 30% 的明显 BENIGN 案例，显著提升处理效率。

### 4.4 七个取证工具说明

| 工具 | 功能 | 批量支持 | 外部依赖 |
|------|------|----------|----------|
| `path_forensics` | 解析 AS_PATH，提取 Origin，识别直接劫持与泄露嫌疑人 | 逐条分析 + 汇总统计 | 无 |

## 5. 使用指南

### 5.1 构建 RAG 知识库

RAG 知识库是系统运行的前提条件。推荐使用合成案例构建默认库：

```bash
# 步骤 1：生成合成 BGP 异常案例（使用 LLM）
python auto_generator/auto_generator.py

# 步骤 2：将案例向量化并构建 ChromaDB
python build_vector_db.py
```

如果已有真实事件摘要，可以使用真实语料构建 RAG：

```bash
# 从已抓取的真实事件生成 RAG 语料
python scripts/build_rag_from_events.py

# 用真实语料构建向量库
python build_vector_db.py --input data/rag_cases_from_events.jsonl
```

> **注意**: `build_vector_db.py` 会删除并重建整个 ChromaDB 目录，不会增量更新。如需保留旧数据，请先备份 `rag_db/` 目录。

### 5.2 抓取真实 BGP 事件

系统支持从多种数据源获取 BGP 事件数据，包括 RIPE RIS MRT 归档文件和 BGPlay 回放数据。数据采集流程包括原始数据下载、可疑更新筛选和事件结构化存储三个步骤。

**基本用法**：

```bash
python scripts/step1_collect_events.py \
  --input data/famous_bgp_events.json \
  --source auto
```

**数据源选择策略**：

- `ris_mrt`：从 RIPE RIS 的 MRT 归档中下载原始 BGP 更新数据，数据最完整但下载量大
- `ripestat`：通过 RIPEstat API 查询，速度快但数据粒度较粗
- `auto`：自动尝试最佳数据源，优先使用 RIPEstat，数据不足时自动降级到 RIS MRT

**四步筛选法详解**：

系统对原始 BGP 更新采用四级递进过滤策略，确保只保留真正可疑的更新进入后续溯源：

1. **前缀过滤**：只保留目标 prefix 相关的 BGP 更新，过滤无关前缀的更新消息
2. **Origin 校验**：比较更新中的 Origin AS 与预期合法持有者，标记不匹配的更新
3. **时间窗口**：严格限定在事件发生的时间范围内，排除无关时段的更新
4. **Valley-Free 拓扑检查**：验证 AS_PATH 是否符合 Valley-Free 策略（Tier-1 到非 Tier-1 再到 Tier-1 即为违规）

经过四步筛选后，每个事件的输出目录包含元信息、可疑更新列表和原始数据三个文件，为后续 Agent 溯源提供结构化输入。

| 参数 | 可选值 | 说明 |
|------|--------|------|
| `--input` | 文件路径 | 事件配置文件，默认为 `data/famous_bgp_events.json` |
| `--source` | `ris_mrt`, `ripestat`, `auto` | 数据源选择；`auto` 模式自动选择最佳数据源 |
| `--output` | 目录路径 | 输出目录，默认为 `data/events/` |

每个事件将在 `data/events/<event_id>/` 下生成三个文件：

| 文件 | 内容 |
|------|------|
| `meta.json` | 事件元信息：event_id, prefix, victim, attacker, 时间窗口, 数据源 |
| `suspicious_updates.json` | 筛选后的可疑 BGP updates 列表 |
| `raw_bgplay.json` | 原始 BGPlay 数据（如果数据源支持） |

### 5.3 单条告警溯源

使用 `BGPAgent.diagnose()` 进行单条告警分析：

```python
import asyncio
from bgp_agent import BGPAgent

async def main():
    agent = BGPAgent()

    alert = {
        "prefix": "8.8.8.0/24",
        "as_path": "3356 4761",
        "detected_origin": "4761",
        "expected_origin": "15169"
    }

    result = await agent.diagnose(alert, verbose=True)
    print(result["final_result"])

asyncio.run(main())
```

### 5.4 批量告警溯源（推荐）

批量模式是本系统的主要工作模式，能利用多条告警间的关联信息提高准确性：

```python
import asyncio
from bgp_agent import BGPAgent

async def main():
    agent = BGPAgent()

    batch = {
        "time_window": {
            "start": "2014-04-01T08:00:00",
            "end": "2014-04-01T18:00:00"
        },
        "updates": [
            {
                "prefix": "8.8.8.0/24",
                "as_path": "3356 4761",
                "detected_origin": "4761",
                "expected_origin": "15169"
            },
            {
                "prefix": "8.8.4.0/24",
                "as_path": "3356 4761 15169",
                "detected_origin": "15169",
                "expected_origin": "15169"
            }
        ]
    }

    result = await agent.diagnose_batch(batch, verbose=True)
    print(f"Status: {result['final_result']['status']}")
    print(f"Attacker: {result['final_result']['most_likely_attacker']}")
    print(f"Confidence: {result['final_result']['confidence']}")

asyncio.run(main())
```

### 5.5 通过命令行批量溯源

系统也支持通过 `bgp_agent.py` 的命令行入口运行：

```bash
# 批量溯源模式

# 单条默认测试案例
python bgp_agent.py
```

### 5.6 使用 performance_test.py 进行标准化评估

```bash
python performance_test.py --events --events-dir data/events
```

该命令将：
1. 从 `data/events/` 加载所有已抓取事件
2. 对每个事件调用 `diagnose_batch()`
3. 将溯源报告保存到 `report/forensics/`
4. 在控制台输出每个案例的判定结果和总体准确率

python scripts/generate_benchmark_synthetic_cases.py \

### 6.3 运行四方法对比实验

四种评估方法定义：

| 方法 | 组成 | 说明 |
|------|------|------|
| M1 | RAG + LLM + Tools | 完整系统，利用全部能力 |
| M2 | 仅 LLM | 无 RAG、无工具，纯推理 |
| M3 | 规则检测 | 基于固定规则，不依赖 LLM |
| M4 | RAG + LLM | 有检索无工具调用 |

**运行合成数据对比实验：**

```bash
python scripts/run_comparative_synthetic.py
```

输出：`report/evaluation/comparative_results_synthetic.json`

**运行真实事件对比实验：**

```bash
# 完整流程（采集 + 构建 RAG + 对比实验）
python scripts/run_comparative_real_pipeline.py --prepare-top10

# 跳过已完成的步骤
python scripts/run_comparative_real_pipeline.py \
  --skip-step1 --skip-rag-jsonl --skip-vector-db
```

输出：`report/evaluation/comparative_results_real.json`

### 6.4 运行指标实验

```bash
python scripts/run_synthetic_metrics_experiment.py \
  --input data/benchmark_synthetic_cases.json \
  --report-out report/evaluation/synthetic_metrics_report.json
```

评估指标：

| 指标 | 说明 |
|------|------|
| 严格准确率 (Strict Accuracy) | 异常类型 + 攻击者 AS 均正确 |
| 攻击者归因准确率 (Attacker Accuracy) | 攻击者 AS 正确（放宽类型要求） |
| 误报率 (FPR) | BENIGN 被误判为恶意类别的比例 |
| 平均时延 (Avg Latency) | 单案例平均处理时间 |
| 置信度-准确率偏差 | 高置信度案例中错误案例的比例 |
| 噪声鲁棒性 | 不同噪声级别下的准确率衰减 |

## 8. 常见问题与故障排除

### 8.1 API 连接问题

**症状**: 运行脚本时报 API 连接超时或认证失败

**解决方案**:
1. 检查 `.env` 文件中的 `DEEPSEEK_API_KEY` 是否正确
2. 确认网络能访问 `https://api.deepseek.com`
3. 尝试运行 `python test-api.py` 进行连通性测试

### 8.2 首次运行下载模型缓慢

**症状**: 首次运行 RAG 相关功能时卡在模型下载

**解决方案**: 设置 HuggingFace 镜像环境变量：

```bash
export HF_ENDPOINT=https://hf-mirror.com
```

模型文件约 90MB，下载后缓存在本地，后续运行无需重复下载。

### 8.3 Neo4j 连接失败

**症状**: 控制台提示 Neo4j 连接失败或 graph_analysis 返回退化结果

**说明**: Neo4j 为可选组件。未连接时 `graph_analysis` 工具会返回退化提示文本，不影响其他工具和整体推理流程。如不需要图分析功能，可忽略此提示。

### 8.4 build_vector_db.py 覆盖旧数据

**症状**: 构建向量库后旧数据丢失

**说明**: `build_vector_db.py` 的行为是全量重建而非增量更新。如果需要保留旧的 RAG 数据，请在运行前手动备份 `rag_db/` 目录。

### 8.5 批量溯源结果不稳定

**症状**: 同一输入多次运行得到不同结论

**可能原因**:
- LLM API 的服务端随机性（即使 temperature=0.0）
- API 版本更新导致模型行为变化
- RAG 检索结果的微小波动

**建议**: 对于关键实验，多次运行取多数结果，或固定随机种子后重新生成 RAG 库。

### 8.6 FORGERY 与 LEAK 分类歧义

**症状**: 短路径场景下系统在 FORGERY 和 LEAK 之间摇摆

**说明**: 这是当前版本的已知局限。短尾伪造路径（路径长度 1-2 跳）可能表现为路由泄露的特征，存在分类歧义。长尾伪造路径的识别更为稳定。建议在分析短路径案例时关注推理链中的具体证据而非仅看最终标签。

### 8.7 脚本运行报 "ModuleNotFoundError"

**症状**: 运行脚本时找不到 `tools` 等模块

**解决方案**: 确保在项目根目录下运行脚本，不要进入 `scripts/` 或 `tools/` 子目录运行。系统使用相对路径导入，依赖项目根目录作为工作目录。

### 8.8 内存不足或 ChromaDB 加载失败

**症状**: 运行过程中出现内存错误或 ChromaDB 初始化失败

**解决方案**:
- ChromaDB 使用内存映射文件，对大量案例（超过 1000 条）建议预留至少 4GB 可用内存
- 如果 ChromaDB 数据损坏，删除 `rag_db/` 目录后重新运行 `build_vector_db.py`
- 对于内存受限环境，可考虑减少合成案例生成数量（修改 `auto_generator.py` 中的生成参数）

### 8.9 RIPEstat API 速率限制

**症状**: `authority_check` 或 `geo_check` 工具返回错误或超时

**解决方案**: RIPEstat API 对请求频率有速率限制。批量处理大量事件时，工具内部已实现请求间隔控制。如果持续遇到限制，可适当增加处理间隔，或使用本地知识库作为兜底方案。需要注意的是，`authority_check` 工具内置了多层降级策略：优先使用 RIPEstat API，API 不可用时自动降级到本地知识库查询，两者均不可用时返回 `UNKNOWN` 标记，不会中断整体流程。

### 8.10 合成案例质量不佳

**症状**: 自动生成的合成案例场景重复或逻辑不合理

**建议**: 合成案例的质量高度依赖 LLM 的生成能力。可以通过以下方式提升质量：
- 在 `config/knowledge_base.json` 中丰富实体配置（增加 victim/attacker/transit AS 的多样性）
- 提高生成并发数 `CONCURRENCY`（默认值为 10），增加生成多样性
- 对生成结果进行人工抽样审核，确保案例的合理性和多样性
- 必要时使用真实事件 RAG 语料替代合成案例

## 9. 工作流程最佳实践

### 9.1 推荐工作流程

对于首次使用本系统的研究人员，建议按照以下顺序逐步熟悉系统功能：

**第一阶段：环境验证** → 安装依赖、配置 API 密钥、运行 `test-api.py` 验证连通性、构建默认 RAG 库。

**第二阶段：小规模实验** → 生成 10-20 条合成案例、用单条模式验证基本推理能力、检查溯源报告的结构完整性。

**第三阶段：正式实验** → 生成 50-100 条合成基准案例（含不同噪声级别）、运行四方法对比实验、运行指标实验、生成评估图表。

**第四阶段：真实事件验证** → 准备真实事件配置、抓取事件数据、运行批量溯源、与合成实验结论进行交叉比对。

### 9.2 实验记录建议

每次实验建议记录以下信息以确保可复现性：

- 合成案例生成的随机种子（`--seed` 参数）
- RAG 库的构建时间和案例数量
- 使用的模型和 API 版本
- 各方法的准确率、时延、置信度分布
- 错误案例的详细溯源报告（便于后续分析改进）

建议为每次重要实验创建独立的实验目录，将配置文件、生成脚本和结果报告统一归档。

### 9.3 结果解读注意事项

在解读实验结果时，需要注意以下几点：

- **严格准确率偏保守**：严格准确率要求类型和攻击者同时正确，实际值通常低于攻击者归因准确率。两种指标互为补充，应同时报告。
- **噪声级别影响显著**：高噪声场景下的准确率通常比低噪声场景低 10-20 个百分点。这种衰减是正常的，反映系统对输入质量的敏感度。
- **置信度不等于准确率**：系统输出的置信度是 LLM 对自身结论的确定性评分，可能偏高。需要结合实际的准确率统计数据来校准置信度的可信度。
- **小样本结论需谨慎**：案例数量少于 20 条时，准确率的统计显著性不足，不宜对外推广为系统性能结论。
